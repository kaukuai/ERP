# 成祥 ERP：研究與功能藍圖

> 本文件保留初版研究基準。最新狀態以 [數碼一號功能對標與驗收](數碼一號功能對標與驗收.md) 及 [v0.2 操作與升級](v0.2操作與升級.md) 為準。

研究更新：2026-11-02。適用目前已確認的方向：單一公司、買賣業、約 20 人使用、不需要自製、倉庫與基本資料可以自行新增、完整取代舊系統；黃單作為報價單或訂單。

## 1. 需求證據與尚未確認的事項

六張截圖顯示舊系統具備報價、訂單、廠商詢價、採購、銷退／進退、前台銷貨、領料與入庫、調撥調整、借還、應收付沖帳、銷售與存貨報表，以及客戶／廠商／產品／組合品建檔等選單。

截圖可證明選單與流程存在，不能證明資料表結構、成本算法、欄位定義、介面可用性、實際資料量、授權方式或可匯出的檔案格式。因此不能僅根據畫面斷言已完成舊系統移轉。

目前還未取得實際產品類型、客戶與商品匯出、期初存貨與成本、應收應付明細、收付款習慣、稅額與折讓規則、使用者分工。這些資料會決定正式切換所需的最後欄位與流程。

## 3. 國外及開源資源比較

| 方案 | 官方可確認的定位 | 本案評估與取捨 |
| --- | --- | --- |
| ERPNext | 開源 ERP；銷售訂單連接交貨、發票與收款；提供庫存預留及受控流水設計 | 適合作為完整 ERP 功能與交易規則的基準。若轉向成熟核心，需另外驗證繁中、台灣帳務、黃單及升級客製 |
| Odoo Community／Enterprise | 開源社群版與商業企業版並存；官方文件有完整庫存與成本模型 | 生態與擴充值得評估；必須逐模組確認版本、授權、維護者與本地支援，不能把企業版功能全算進社群版 |
| Dolibarr | 模組化 ERP／CRM，涵蓋往來、報價訂單、帳款、庫存、會計與文件等 | 可參考中小企業作業與單據產出；是否足以涵蓋公司的進階控管仍需情境試用 |
| Tryton | 官方列有會計、銷售、庫存、採購、供應鏈等整合功能；伺服器連接 PostgreSQL | 適合評估模組邊界與資料模型；繁中體驗、台灣介接及可承接的維運團隊需要另外確認 |

ERPNext 的銷售文件將草稿、送出、預留與交貨區分；其預留不等於實際庫存出入。本案據此採用可檢核的分段流程。[銷售訂單](https://docs.frappe.io/erpnext/sales-order)、[庫存預留](https://docs.frappe.io/erpnext/stock-reservation)。

流水更正應保留原始紀錄及可追溯後續效果。本案的庫存、總帳與稽核資料設置防刪改觸發器；這是應用與資料庫控制，仍須搭配伺服器與檔案權限。[ERPNext 不可變流水說明](https://docs.frappe.io/erpnext/immutable-ledger-in-erpnext)。

成本方法應明確選擇，不能把出貨順序、參考成本與存貨評價混成一件事。本版採每商品、每倉的移動加權平均；採購進價與出貨時實際成本分別保留。[Odoo 成本方法文件](https://www.odoo.com/documentation/19.0/applications/inventory_and_mrp/inventory/inventory_valuation/cheat_sheet.html)、[庫存異動評價](https://www.odoo.com/documentation/19.0/applications/inventory_and_mrp/inventory/inventory_valuation/operations_valuation.html)。

原始碼入口：[ERPNext](https://github.com/frappe/erpnext)、[Odoo](https://github.com/odoo/odoo)、[Dolibarr](https://github.com/Dolibarr/dolibarr)；功能與架構入口：[Dolibarr 模組表](https://wiki.dolibarr.org/index.php/What_Dolibarr_Do)、[Tryton](https://www.tryton.org/)、[Tryton 部署與架構](https://www.tryton.org/download)。

## 4. 授權與採用方式

ERPNext 的授權是 GPLv3；Frappe Framework 本身為 MIT。Odoo 19 Community 為 LGPLv3，Enterprise 是另一套商業授權。Dolibarr 專案說明為 GPL v3 或更新版本。實際引入程式、模組或散布產品時，應以選定版本各自的授權檔案為依據；本文件不對公司特定的散布方式作法律結論。[Frappe 官方授權](https://docs.frappe.io/legal/others/license-and-trademark)、[Odoo 官方授權](https://www.odoo.com/documentation/19.0/legal/licenses.html)、[Dolibarr 專案授權說明](https://github.com/Dolibarr/dolibarr)。

本次採用自行撰寫的買賣核心與介面，執行時使用 Node.js 內建功能，沒有將上述 ERP 專案安裝或嵌入本系統。採用自研核心可快速驗證公司工作流，但公司也必須承擔後續功能、資料移轉、資安與維運成本。

**建議的長期決策**：用同一組公司情境與移轉資料，同時評估本核心與 ERPNext／Odoo 的差距。若需求擴及完整票據、多公司、多幣、複雜稅務、售後服務或多層簽核，應比較成熟核心加客製與持續自研的總成本。這是本案的工程判斷，不是官方產品的優劣結論。

## 6. 正式替換的工程準則

資料一致性比選單數量更重要。公司要有一致的品號、客戶代號與倉庫代號；每筆庫存變動能追到來源；未交、預留、未結餘額與總帳能相互驗證；更正要留痕；備份必須能還原。

20 人同時使用並不直接決定資料庫選型。單一伺服器、小型交易量可以先以本版驗證，但寫入頻率、資料總量、長查詢、可用性與備援要求會影響最後選擇。SQLite 官方說明了與客戶端／伺服器資料庫的不同使用情境；多程序、高並行與多節點需求應重新評估 PostgreSQL 等架構。[SQLite 適用情境](https://sqlite.org/whentouse.html)。

電子發票必須區分「列印報價／訂單」、「查詢發票 API」與「真正開立並回傳發票」。本版黃單不作為統一發票。正式開立要針對選定服務與公司的資格、測試流程及規格另外實作，不能由查詢 API 規範推定已具備開立能力。[財政部 API 使用規範](https://law-out.mof.gov.tw/LawContent.aspx?id=GL010122)。
