# 雲端部署

## 先做互動展示：不需獨立後端

本版預設提供可直接操作的線上展示。沒有設定正式後端網址時，網站會使用虛構資料，按「進入示範工作空間」即可操作報價、訂單、採購、庫存、帳款、POS、列印與匯出，不需要先建立後端主機、磁碟或代理密鑰。

部署步驟：

1. 取得包含 v0.4.2 的最新程式，讓網站部署該提交；舊版提交不會自動取得新功能。
2. Root Directory 指向儲存庫根目錄，Framework 選 Other，讓 `vercel.json` 指定建置指令。清除專案內舊的 Build Command／Output Directory 覆寫，使用本版的 Build Output v3。
3. 沒有設定 `ERP_BACKEND_URL` 時自動啟用展示。若之前已填入後端網址或模式設定，將 `ERP_MODE` 設為 `demo` 後重新部署即可明確切到展示。
4. 開啟網址，按「進入示範工作空間」。頂端會顯示「網頁展示模式」及「重新開始展示」。

每個分頁有自己的展示資料與登入。重整可接續該分頁的操作，新的獨立分頁從原始示範資料開始；列印視窗會取得目前單據的展示資料。關閉分頁、八小時未操作、重新部署或按下重置可能清除變更。僅供示意，請使用虛構資料；展示收銀不會實際扣款或退款，也不會開立正式發票。

展示版沿用實際 ERP 交易邏輯。短暫資料庫在請求完成後清除，狀態經驗證加密後由分頁保存，因此不用依賴某一台函式執行個體保留檔案。建置私鑰僅在函式產物內，重新部署會換新私鑰；它不公開、不提交 Git，也不需要使用者手動設定。展示狀態不能用作正式帳套儲存。

自訂網域如未列於平台提供的網址，將完整主機名稱加入 `ERP_ALLOWED_HOSTS`，不要填協定或使用萬用字元。

## 單機正式操作：後端就在同一台電腦

安裝 Node.js 24 後，執行 `start.cmd` 或 `npm run dev:company`，以瀏覽器開啟 `http://127.0.0.1:4320`。網頁服務與 SQLite 都在本機運作，不需另租後端主機；關閉程式後資料仍留在 `data/company.sqlite` 及同層公司目錄。再啟動相同指令即可接續，請保存完整資料與定期備份。

`demo.cmd`／`npm run dev` 是另一個本機虛構示範庫，與線上短暫展示及正式公司庫分開。

## 正式雲端操作：需要持久化後端

正式帳套需一個長期運作的後端程序及持久磁碟；多公司資料庫、備份與根庫須一起保存。此時明確設定 `ERP_MODE=production`，網站入口將交易代理到設定好的 HTTPS 後端。正式模式若缺少後端設定會回傳設定說明，不會偷偷切換成展示。

## 建置成功卻出現 500

`FUNCTION_INVOCATION_FAILED` 表示函式執行失敗，確切拋錯須查看 Runtime Logs，建置紀錄不足以確認。舊版直接以 `src/server.mjs` 執行，預設在程式目錄建立 SQLite，且只允許本機 Host；這不適合函式平台的檔案系統與執行方式。

新版以 Build Output v3 指定正確函式入口。展示模式可直接操作；只有明確指定正式模式卻未設定後端時，首頁才會顯示部署步驟，API 回傳 `503 ERP_DEPLOYMENT_NOT_CONFIGURED`。不會建立暫存正式帳套或偷偷改用記憶體資料庫。`/tmp` 會隨執行個體消失，亦無法讓多個函式共用同一份交易，因此不能作正式儲存。

使用者回報的部署提交 `e8128dd` 不包含這些修正。請部署包含 v0.4.2 的最新提交，重新部署舊提交無法取得展示功能。設定中若已有舊的 Build Command、Output Directory 或 Framework 覆寫，清除覆寫，讓儲存庫的 `vercel.json` 生效。

## 正式雲端步驟 1：啟動持久化後端

若尚無主機，可在 Render 建立 Blueprint，連接本儲存庫並選擇包含目前版本的最新提交，以根目錄 `render.yaml` 建立後端。這份模板使用付費執行方案及 10 GB 持久磁碟；建立前請在平台畫面確認當期費用與區域。

建立時將 `ERP_ALLOWED_HOSTS` 填為實際前台網域，不含協定。平台自動產生不同的 `ERP_PROXY_SECRET` 與 `ERP_SETUP_KEY`，並提供後端 HTTPS 網址；後端會精確允許平台設定的自身網域。將後端網址及代理密鑰填入下一節的網站環境；初始化密鑰只在第一次建立帳套時使用。不要將兩把密鑰貼到聊天或加入 Git。

此模板為單一後端與一份磁碟，關閉自動部署；升級時先備份、驗證副本，再由平台執行部署。免費暫存檔案系統無法替代此持久磁碟。託管平台的真實建立、TLS 與服務區域仍需在實際帳號中驗證。

若自行管理主機，使用以下容器與 HTTPS 設定：

準備可執行容器的主機、固定磁碟及一個指向該主機的後端網域。這是獨立於網站入口的服務；將前台網址填作後端會形成迴圈，程式會拒絕。

```sh
git clone --branch feature/erp-missing-workflows https://github.com/kaukuai/ERP.git
cd ERP
cp deploy/backend.env.example .env
```

在主機的 `.env` 填入：

| 變數 | 值與用途 |
| --- | --- |
| `ERP_BACKEND_HOST` | 後端實際網域，不含協定或路徑；DNS 指向本主機 |
| `ERP_ALLOWED_HOSTS` | 後端、前台與需要使用的預覽網域，以逗號分隔，逐一列出，不使用萬用字元 |
| `ERP_PROXY_SECRET` | 前後端共用的隨機代理密鑰，至少 32 字元 |
| `ERP_SETUP_KEY` | 不同於代理密鑰的隨機初始化密鑰，至少 32 字元 |

兩把密鑰應各自使用安全密碼產生器產生，保存在部署服務的 Secret 或主機受控檔案中；不要提交 Git、放在網址或貼入聊天。範例檔刻意不提供可用的預設密鑰。

```sh
docker compose up -d --build
docker compose ps
```

`https` 服務自動管理後端 HTTPS 憑證，需正確 DNS 並能由外網連入 80／443。後端只在容器網路公開 4320，健康檢查使用 `/healthz`。第一次建立帳套時，管理員在畫面輸入 `ERP_SETUP_KEY`；初始化完成後仍使用自己的帳密登入。

`erp-data` 掛載至 `/var/lib/erp`，包含 `company.sqlite`、`.company-workspaces/` 及 `backups/`。單純重建映像或 `docker compose restart` 保留此卷；**不要執行 `docker compose down -v`，這會刪除資料卷。** 一台後端、一份本機卷；不要啟動多個程序共用網路檔案，亦不要將服務自動擴充為多個副本。

容器入口先修正固定資料卷的擁有者，再降為 `node` 使用者啟動後端；應用程序不以 root 運作。這也處理新掛載的託管磁碟初始屬於 root 的情況。

既有資料請先按 v0.4 升級說明備份與驗證副本，再於停機維護時將根庫、公司庫及目錄關聯移入此卷，設定正確檔案權限。不要只放入根庫卻遺漏其他帳套，也不要以空庫蓋掉原資料。

## 正式雲端步驟 2：設定網站入口

Vercel 專案 Root Directory 指向本儲存庫，使用 Node.js `24.x`。在 Environment Variables 設定：

| 變數 | 值與用途 |
| --- | --- |
| `ERP_MODE` | 正式帳套設定為 `production` |
| `ERP_BACKEND_URL` | 後端完整 HTTPS 原點，例如 `https://erp-backend.example.invalid`；換成實際網域，不含路徑、帳密或查詢參數 |
| `ERP_PROXY_SECRET` | 與後端完全相同的代理密鑰 |
| `ERP_ALLOWED_HOSTS` | 使用的自訂前台網域，逗號分隔；平台提供的本次網址、分支網址及正式專案網址會從平台變數精確加入 |

網站入口不需要 `ERP_DB`、`ERP_HOST` 或 `ERP_SETUP_KEY`。後端的 `ERP_ALLOWED_HOSTS` 也必須包含實際前台網域；任意新預覽網址不會自動獲得正式後端信任。建議以固定測試網域接測試後端，正式網域接正式後端，分開環境變數與資料卷。

選擇包含目前版本的最新提交重新部署。首頁若顯示設定步驟，確認環境變數套用到正確的 Production／Preview 環境後再 Redeploy；只儲存變數不會更新既有部署。

登入 Cookie 保留 HttpOnly、SameSite=Strict 與 Secure；公司 Cookie、CSRF、冪等碼及角色檢查仍在後端處理。代理只接受精確允許的前台 Host，覆寫客戶自行傳入的代理標頭；後端以獨立密鑰驗證公開 Host／協定，不能只信任 `X-Forwarded-Host`。

## 正式雲端步驟 3：驗收與維運

1. 前台與後端的 `/healthz` 回傳 `ok: true`；`/api/status` 顯示目前版本，沒有暴露資料庫路徑或密鑰。
2. 輸入初始化密鑰建立測試帳套；登出再登入，建立測試商品並完成一筆交易。
3. 重啟後端，再確認商品、單據、獨立帳套與庫存／帳務一致性仍在。
4. 管理員逐公司下載備份，另外將備份保存至不同主機；定期演練還原。單次 API 備份只包含目前公司。

測試已覆蓋本機實際 HTTP 代理、初始化、Secure Cookie、CSRF、來源拒絕、冪等、公司隔離、二進位備份及後端重啟保留。這不等於已驗證使用者的正式域名、TLS、實際平台部署、異機災難還原或長時間負載。

常見錯誤：`503` 表示入口缺設定或前後端網址相同；`502` 表示後端連線失敗／逾時；`403` 請核對前後端代理密鑰、前台允許網域及 Origin。舊版仍出現泛用 `500` 時，確認部署提交與 Root Directory，再查看函式 Runtime Logs；提供錯誤類型與堆疊即可，不需提供 Cookie、密鑰或帳密。

平台行為可查閱 [Node 執行環境](https://vercel.com/docs/functions/runtimes/node-js) 與 [函式限制](https://vercel.com/docs/functions/limitations)。
